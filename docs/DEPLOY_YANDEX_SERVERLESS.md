# Перенос бота «Междуречие» на Yandex Cloud Serverless

> **⚠️ ОБНОВЛЕНО 25.11.2026 — RAG-версия.** Проект работает по RAG-схеме
> (LlamaIndex): и генерация (LLM), и эмбеддинги ходят через OpenRouter API
> (`OPENROUTER_API_KEY`), локального PyTorch нет — пакет лёгкий и в лимиты
> Cloud Functions помещается. Что изменилось относительно инструкции ниже:
> - вместо `rules.db` (SQLite) — `rules.json` (готовит `python -m bot.sync`);
> - переменные окружения: нужен только `OPENROUTER_API_KEY` (опционально
>   `LLM_MODEL` / `EMBED_MODEL`); прежние переменные LLM и `DB_FILE_PATH`
>   не используются;
> - кэш векторов `rules.embeddings.npz` на холодном старте пуст (/tmp чистая) —
>   первая сборка индекса делает ~6 запросов к OpenRouter, тёплые вызовы — ноль;
> - инструкция ниже описывает прежнюю схему — разделы про `rules.db`
>   (бакет и zip) читать как «rules.json вместо rules.db».

Инструкция для разработчика, который переносит бота с локального запуска
(`python main.py`) на бессерверный стек Yandex Cloud (Cloud Functions + API
Gateway + Object Storage).

> Бот хостится на **аккаунте Yandex Cloud разработчика** (по договорённости с
> владельцем). Грант 4000 ₽ / 60 дней + free tier покрывают эту нагрузку
> практически в 0 ₽. Источник истины по коду — репозиторий GitHub
> `imyartsev/bot2reki`: все правки идут через него, сервер только разворачивает
> то, что в репозитории.

## 0. Что меняется по сравнению с текущим ботом

| Сейчас (локально) | После (serverless) |
|---|---|
| `main.py` запускает два вечных цикла | Вечных циклов нет — функция просыпается на каждый запрос |
| Telegram: `dp.start_polling` | Telegram **webhook** → API Gateway → функция |
| ВК: vkbottle `bot.run_forever` (long-poll) | ВК **Callback API** → API Gateway → функция |
| `rules.db` лежит на диске, читается | `rules.db` кладётся в zip, открывается `mode=ro` |
| Секреты в `.env` | Секреты в переменных окружения функции |
| `sync.py` строит БД на той же машине | `sync.py` гоняется **локально**, готовый `rules.db` кладётся в пакет |

`main.py`, `handlers.py` (бизнес-логика Telegram), `search.py` (RAG + LLM),
`sync.py` — **логику менять не нужно**. Нужен новый слой входа (webhook-адаптер)
и переписанный ВК-обработчик.

## 2. Код (уже в репозитории — писать ничего не нужно)

Весь serverless-слой уже лежит в репозитории. Бизнес-логику (`handlers.py`,
`search.py`, `sync.py`) трогать не надо. Работа на сервере — **собрать пакет и
настроить Yandex** (разделы 3–5), а не писать код.

Ключевые файлы:

| Файл | Роль |
|---|---|
| `serverless_handler.py` | Точка входа функции. Различает три входа: async-задание (есть ключ `__job__`), ВК Callback (`type`), Telegram (`update_id`). |
| `bot/async_jobs.py` | Механизм асинхронного само-вызова: подпись задания, IAM-токен, отправка. Общий для Telegram и ВК. |
| `bot/vk_callback.py` | ВК Callback API: быстрый ответ VK + асинхронный воркер (LLM, документы). |
| `bot/handlers.py` | Telegram: быстрый ответ + асинхронный воркер `process_tg_job`. |
| `bot/search.py`, `bot/sync.py` | Без изменений. |

Точка входа в настройках функции: **`serverless_handler.handler`**.

> Runtime Yandex Cloud сам запускает event loop и поддерживает `async def handler`
> — отдельно `asyncio.run(...)` вызывать НЕ нужно.

### 2.1. Почему оба мессенджера работают через асинхронный само-вызов

И Telegram, и ВК ждут ответ на webhook считанные секунды, а ответ LLM занимает
десятки секунд. При синхронной обработке мессенджер рвёт соединение
(в логах функции `ERROR Code: 499 Request cancelled`, в логах шлюза `499`, при
упёршемся шлюзе `504`), функция убивается **до** отправки ответа, и житель не
получает ничего.

Поднимать таймаут функции бесполезно и вредно: он лишь перекладывает отказ на
клиента. Telegram после неудачи уходит в ретраи с нарастающей паузой — на проде
ответ доходил через 8 минут, а иногда сообщения копились в очереди часами
(`pending_update_count` в `getWebhookInfo`).

Решение в коде: медленная работа уходит в **асинхронный само-вызов** функции
(`https://functions.yandexcloud.net/<FUNCTION_ID>?integration=async`, IAM-токен
берётся из metadata-сервиса). Механизм общий — `bot/async_jobs.py`:

- **Telegram** (`bot/handlers.py`): на текстовый вопрос функция отправляет
  «Ищу ответ в документах…», возвращает шлюзу `200` за доли секунды и ставит
  задание в очередь. Ответ присылает воркер `process_tg_job`. Команды `/start`,
  `/help`, `/about`, кнопки и документы (33–44 КБ) отвечают синхронно.
- **ВК** (`bot/vk_callback.py`): статика (`начало`, `помощь`, «О боте»,
  «Написать администратору») отвечает синхронно, документы и вопросы к LLM
  уходят в воркер `process_vk_job`.

Задание подписывается HMAC-SHA256 на `JOB_SECRET` (по умолчанию = `VK_SECRET`),
обработчик проверяет подпись и отклоняет всё, что пришло с `httpMethod`.

Если `FUNCTION_ID` не задан, async-вызов не прошёл или вернул не `202` — задание
выполняется инлайн. Медленно и с риском ретрая, зато житель получает ответ.

Ответы длиннее 4096 символов Telegram отбрасывает целиком, поэтому воркер режет
их на части.

> **Безопасность async-ветки.** Функция публичная, её можно дёрнуть напрямую в
> обход API Gateway. Поэтому задание само-вызова подписывается HMAC-SHA256 на
> `VK_SECRET`, а обработчик проверяет подпись и отклоняет всё с `httpMethod` —
> сторонний вызов без знания `VK_SECRET` получит `403`. Отдельной настройки не
> требует, но `VK_SECRET` должен быть задан.

> **Это требует двух вещей от инфраструктуры (раздел 4):** включить
> **асинхронный вызов** функции и задать переменную **`FUNCTION_ID`** (= ID самой
> функции). Без них само-вызов вернёт `412 async invocation is disabled` и вопрос
> снова не дойдёт. Если `FUNCTION_ID` не задан, код выполнит задание инлайн (как
> резерв для локального запуска) — но на сервере это вернёт прежний 499.

### 2.2. ВК работает через Callback API, не long-poll

vkbottle-шный `run_forever()` на serverless не выживает. В `bot/vk_callback.py`
vkbottle оставлен только как **клиент VK API** (`vkbottle.API`) — для отправки
сообщений и загрузки документов. Bot/labeler/polling выброшены. Клавиатура и
ветки документов перенесены из `bot/vk_bot.py`.

### 2.3. БД открывается read-only — уже в коде

В функции файловая система только для чтения (писать можно лишь в `/tmp`). В
`bot/search.py` подключение к БД уже открыто как
`sqlite3.connect(f"file:{db_path}?mode=ro", uri=True)` — менять ничего не нужно.
На сервере задать переменную `DB_FILE_PATH=rules.db` (путь внутри пакета).

### 2.4. `requirements.txt` для функции

В репозитории есть `requirements-serverless.txt` — урезанный набор (без `openpyxl`
и `python-dotenv`, они нужны только офлайн-скрипту `sync.py`). При сборке пакета
положить его в архив **под именем `requirements.txt`** (см. раздел 3).

> Можно залить и общий `requirements.txt` — `openpyxl`/`python-dotenv` просто
> увеличат размер пакета, но не помешают.

### 2.5. Переменные окружения — уже в коде

В `config/settings.py` уже читаются `VK_CONFIRMATION`, `VK_SECRET` и `FUNCTION_ID`
(рядом с остальными `os.getenv`). Значения задаются в настройках функции (раздел 4).

`load_dotenv()` в settings можно оставить — без файла `.env` это no-op, значения
придут из переменных окружения функции.

## 3. Собрать пакет функции

1. Локально собрать актуальную БД из Excel:
   ```bash
   python -m bot.sync data/rules.xlsx rules.db
   ```
2. Собрать zip с кодом и данными. В архив должны попасть:
   - `serverless_handler.py`
   - папка `bot/` (включая новый `vk_callback.py`)
   - папка `config/`
   - папка `data/` (оба `.docx`)
   - `rules.db` (собранный в шаге 1)
   - `requirements-serverless.txt` → переименовать в `requirements.txt` внутри пакета
   ```bash
   zip -r function.zip serverless_handler.py bot config data rules.db requirements.txt
   ```

> `rules.db` в пакете остаётся запасной базой. Рабочая база живёт в бакете Object
> Storage (раздел 4а) и обновляется без пересборки пакета.

## 4. Настроить Yandex Cloud

1. **Каталог (folder).** В консоли создать каталог, например `mezhdureche-bot`.
2. **Сервисный аккаунт.** Создать сервисный аккаунт, выдать роли `editor` и
   `serverless.functions.invoker`.
3. **Функция.** Создать ресурс Cloud Functions:
   - среда выполнения **Python 3.11**;
   - способ загрузки — **ZIP-архив**, прикрепить `function.zip`;
   - точка входа — **`serverless_handler.handler`**;
   - память — **512 МБ** (индекс фрагментов + зависимости; 128 МБ мало);
   - таймаут — **60 секунд** (столько нужно async-воркеру на ответ LLM;
     занижать нельзя — короткий лимит убьёт воркер на середине запроса);
   - сервисный аккаунт — созданный выше;
   - сделать функцию **публичной**;
   - переменные окружения:
     `TELEGRAM_BOT_TOKEN`, `VK_TOKEN`, `OPENROUTER_API_KEY`,
     `VK_CONFIRMATION=<строка из настроек сообщества>`,
     `VK_SECRET=<придуманный секрет>`.
     (`FUNCTION_ID` добавляется на шаге 4 ниже — он известен только после создания
     функции.)
4. **Асинхронный вызов функции (обязательно для Telegram и ВК).** Сразу после создания функции:
   - на странице функции скопировать её **идентификатор** (поле «Идентификатор»,
     вида `d4xxxxxxxxxxxxxxxxxx` — это не version id) → добавить переменную
     окружения `FUNCTION_ID=<этот идентификатор>` и **создать новую версию**;
   - вкладка **«Асинхронный вызов»** → включить, число повторов 1–2, сохранить.

   Это даёт функции возможность дёргать саму себя в фоне (раздел 2.1). Без этого
   вопросы к LLM падают с `499` в логах шлюза, а статика (`начало`, `/start`)
   при этом работает — характерный признак незаданного `FUNCTION_ID` /
   выключенного async-вызова. Касается обоих мессенджеров. Сервисный аккаунт уже имеет роль `serverless.functions.invoker`
   (шаг 2) — она и используется для само-вызова.
5. **API Gateway.** Создать API-шлюз, в спецификацию добавить два маршрута на одну
   и ту же функцию (подставить `function_id` и `service_account_id`):

   ```yaml
   paths:
     /tg-webhook:
       post:
         x-yc-apigateway-integration:
           type: cloud_functions
           function_id: <FUNCTION_ID>
           service_account_id: <SERVICE_ACCOUNT_ID>
         operationId: tg
     /vk-callback:
       post:
         x-yc-apigateway-integration:
           type: cloud_functions
           function_id: <FUNCTION_ID>
           service_account_id: <SERVICE_ACCOUNT_ID>
         operationId: vk
   ```

   Запомнить «Служебный домен» шлюза, например
   `https://<id>.apigw.yandexcloud.net`.

## 5. Подключить webhooks

### Telegram
Открыть в браузере (подставить токен и домен шлюза):
```
https://api.telegram.org/bot<TELEGRAM_BOT_TOKEN>/setWebhook?url=https://<id>.apigw.yandexcloud.net/tg-webhook
```
Ответ `{"ok":true,...,"description":"Webhook was set"}` — успех.

### ВКонтакте
> Перед этим убедиться, что функция развёрнута, `FUNCTION_ID` задан и
> **асинхронный вызов включён** (раздел 4) — иначе подтверждение пройдёт, но
> вопросы к боту будут падать с 499.

В сообществе: **Управление → Настройки → Работа с API → Callback API**:
1. Адрес: `https://<id>.apigw.yandexcloud.net/vk-callback`
2. Версия API — актуальная (например `5.199`).
3. Скопировать **строку подтверждения** — короткий токен под заголовком «Строка,
   которую должен возвращать сервер» (не путать с примером запроса
   `{"type":"confirmation","group_id":...}`, который VK показывает рядом). Положить
   её в переменную `VK_CONFIRMATION` функции, **создать новую версию**, дождаться,
   пока станет активной, затем нажать «Подтвердить» в ВК.
4. Задать **секретный ключ** → тот же в `VK_SECRET`.
5. В разделе «Типы событий» включить **Входящее сообщение** (`message_new`).
6. **Long Poll API выключить.** VK доставляет события либо через Long Poll, либо
   через Callback — одновременно не работает. Убедиться, что Long Poll API
   отключён, чтобы сообщения шли на Callback.

> Проверка эндпоинта до клика «Подтвердить»:
> `curl -X POST <адрес> -H "Content-Type: application/json" -d '{"type":"confirmation","group_id":<id>}'`
> должен вернуть ровно строку подтверждения и код 200.

## 6. Проверка (smoke-test)

- Telegram: написать боту `/start`, затем вопрос по решениям. В разделе **Логи**
  функции — три записи (старт, ответ, отчёт), код 200.
- ВК: написать в сообщество `начало` (ответ мгновенный — статика), затем вопрос по
  решениям. На **вопрос** в логах функции будет **две** записи: быстрый HTTP-вызов
  (код 200, вернул `ok` за доли секунды) и отдельный async-вызов (считает LLM и
  шлёт ответ). Ответ приходит в чат с задержкой в несколько секунд.
- Если в логах шлюза на вопрос виден `499 Request cancelled`, а ответа нет — не
  задан `FUNCTION_ID` или выключен async-вызов (раздел 4).
- Если ошибка — смотреть **Логи функции** в консоли, там трейсбек.

## 4а. База решений в Object Storage (обновление без передеплоя)

Код: `bot/source.py`. Функция на холодном старте качает `rules.db` из бакета в
`/tmp`, потом не чаще раза в 5 минут спрашивает бакет, не сменился ли файл (по
ETag; без изменений файл не качается). Бакет недоступен — бот работает на последней
скачанной базе, а если не скачал ни разу — на `rules.db` из пакета.

Настройка (один раз):
1. **Бакет.** Object Storage → создать бакет, например `mezhdureche-rules`, в том же
   каталоге. Доступ на чтение — **закрытый** (в базе личные данные жителей).
2. **Права функции.** Сервисному аккаунту функции нужна роль `storage.viewer` на
   бакет. Если у аккаунта уже роль `editor` на каталог (раздел 4, шаг 2) — она это
   покрывает, ничего добавлять не нужно.
3. **Права на загрузку.** Тому, кто будет обновлять базу (Иван), выдать на бакет
   роль `storage.uploader` (или `storage.editor`), чтобы он загружал файл через
   консоль сам.
4. **Загрузить** `rules.db` в корень бакета под именем `rules.db`.
5. **Переменные функции:** `DB_S3_BUCKET=<имя бакета>`. Необязательные:
   `DB_S3_KEY` (по умолчанию `rules.db`), `DB_REFRESH_SECONDS` (по умолчанию `300`).
   `DB_FILE_PATH=rules.db` оставить — это запасная база. Пересобрать пакет с новым
   кодом (`git pull`) и **создать новую версию функции**.
6. **Проверка.** Задать боту вопрос; в логах функции должна быть строка
   `База из бакета: <бакет>/rules.db, … байт, версия "…"`. Если вместо неё
   `Не удалось обновить базу из бакета (бакет вернул HTTP 403 …)` — не хватает роли
   из шага 2.

## 4б. История переписки в Object Storage (уточняющие вопросы)

Код: `bot/history.py`. Бот помнит последние сообщения каждого жителя, чтобы
понимать уточнения («а если их шестеро?»). Модели уходят последние 10 сообщений
разговора, только за последний час, каждое обрезано до 1000 символов. Один
JSON-объект на разговор: `history/<tg|vk>/<чат>/<житель>.json`. Команды `/start`
(Telegram) и `старт`/`начало` (ВК) стирают историю жителя.

Бакет отдельный от `rules.db`: история не пропадает при замене базы решений, а у
функции нет права записи туда, где лежит база.

Настройка (один раз):
1. **Бакет.** Object Storage → создать бакет, например `history-2reki`, в том же
   каталоге. Доступ — **закрытый** (переписка жителей — личные данные).
2. **Автоудаление.** В бакете → «Жизненный цикл» → правило: префикс `history/`,
   «Удаление объектов» через **7 дней**. Объект перезаписывается при каждом
   сообщении, так что переписка исчезает через 7 дней после последнего вопроса
   жителя. Код вдобавок выбрасывает сообщения старше 7 дней при каждой записи.
3. **Права функции.** Сервисному аккаунту функции — роль `storage.editor` на этот
   бакет (читать, писать, удалять). Если у аккаунта роль `editor` на каталог —
   ничего добавлять не нужно.
4. **Переменная функции:** `HISTORY_S3_BUCKET=<имя бакета>`. Необязательные (со
   значениями по умолчанию): `HISTORY_MAX_MESSAGES=10`, `HISTORY_WINDOW_MINUTES=60`,
   `HISTORY_MESSAGE_CHARS=1000`, `HISTORY_RETENTION_DAYS=7` (держать равным сроку
   из шага 2). Пересобрать пакет и создать новую версию функции.
5. **Проверка.** Спросить бота «Сколько стоит баня для гостей?», затем «А если их
   будет шестеро?» — второй ответ должен быть про лимит в 4 человека. В логах
   воркера — `история: 2`. В бакете появится объект `history/tg/…/….json`.

Отказы. Бакет недоступен или нет прав — бот отвечает без истории, в логах строка
`ERROR bot.history: История …: прочитать не удалось (бакет истории вернул HTTP 403
на GET) — отвечаю без истории`. Без переменной `HISTORY_S3_BUCKET` история живёт
только в памяти тёплого экземпляра функции (в логах предупреждение
`HISTORY_S3_BUCKET не задан`).

Стоимость: при десятках сообщений в день — около 1 500 записей и 1 500 чтений в
месяц при бесплатных 10 000 и 100 000; объём — килобайты. В рамках бесплатного
лимита, 0 ₽.

---

## 7. Как обновлять архив решений потом

1. Локально: внести решения в `data/rules.xlsx` и собрать `rules.db`
   (`python -m bot.sync data/rules.xlsx data/rules.db`).
2. Загрузить `rules.db` в бакет поверх старого (то же имя `rules.db`).
3. Всё. Бот подхватит новую базу в течение 5 минут, пересобирать пакет не нужно.
   В логах — `RulesEngine: база обновлена до версии …`.

Без бакета (переменная `DB_S3_BUCKET` пуста) — по-старому: положить `rules.db` в
пакет, пересобрать `function.zip`, создать новую версию функции.

## 8. Подводные камни (коротко)

- **vkbottle long-poll не выживает** на serverless — только Callback API (раздел 2.2).
- **ВК-таймаут vs LLM.** VK ждёт `ok` несколько секунд, LLM дольше →
  обязателен асинхронный само-вызов (раздел 2.1) + `FUNCTION_ID` + включённый
  async-вызов функции. Симптом поломки: `начало` отвечает, вопрос — нет, в логах
  шлюза `499`.
- **Файловая система read-only** — БД открыта `mode=ro`, писать только в `/tmp`.
- **Холодный старт.** Первый запрос после простоя медленнее (поднимается контейнер
  + строится векторный индекс; при пустом кэше /tmp добавятся запросы к
  OpenRouter). Это норма для serverless.
- **Дубли в ВК.** Маловероятны: HTTP-обработчик возвращает `ok` мгновенно, до
  ретрая VK. Если всё же проявятся — дедуп по `data["event_id"]` (хранить
  обработанные id в YDB / Object Storage).
- **Промпт = только найденные фрагменты.** В промпт LLM уходят топ-12 фрагментов
  по вопросу (RAG); векторы фрагментов кэшируются в `rules.embeddings.npz`,
  поэтому тёплый инстанс собирает индекс без обращений к OpenRouter.
- **Лимит выполнения.** Таймаут функции должен покрывать ответ LLM; 60 секунд
  с запасом.
